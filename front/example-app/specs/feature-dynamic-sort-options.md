# Feature: Sort options from the API

## Status: implemented - checked in Chrome on 2026-10-12 after the fixtures reload (paper shop fr/en/de, toolbox en). Not checked: a back-office change of a category's default sort, a location field (the demo has none), the options request failing.

## Labels: data fixed, four overridden here (2026-10-12)

- **Fixed in the demo data** (`api/packages/gally-sample-data`): every custom field's
  `defaultLabel` is now English (it was French), so a shop with no label of its own for another
  shop's field shows English. `created_at` moved to `common/` and is labelled in all three shops;
  `name` is labelled in all three shops ("Nom" in French). The paper shop is generated by
  `tools/build.py` from `tools/papershop/manifest.yaml`.
- **Overridden in the storefront**: the API returns fixed English for `_score` ("Relevance"),
  `category__position` ("Position"), `price__price` ("Price") and `stock__status` ("Stock
  status"), whatever the catalog. `useSortOptions` replaces those four labels with
  `common.json` `sort.fields.*`. Logged in `missing-features.md` as a workaround.
- **Hidden in the storefront**: sortable fields are global, so each shop would list the other
  shops' sortable fields (the paper shop would show "Pipe diameter (mm)"). `useSortOptions` drops
  fields carrying another demo shop's prefix (`SHOP_FIELD_PREFIXES`). Logged in
  `missing-features.md`.

## Page/Component: src/components/SortSelect.tsx, src/components/Icon.tsx, src/hooks/useSortOptions.ts, src/hooks/useSearch.ts, src/sdk/server.ts, src/views/CategoryPage.tsx, src/views/SearchPage.tsx, src/locales/{en,fr,de}/{common,category,search}.json, src/styles.css (`.products-sort`)

## Problem

Both listings hardcoded their sort `<option>`s, and the two lists had drifted apart (the category
page had "Name Z-A", the search page did not). Any field a merchant marks "used for sort by" in the
back-office never reached the storefront, and the category page could not show which default sort
the merchant had configured.

The API already had everything:

- `productSortingOptions(localizedCatalog:)` lists the sortable fields with localized labels.
  `SearchManager.getProductSortingOptions(localizedCatalog?)` wraps it. The parameter and the
  per-catalog cache were added to the SDK for this change; before, it cached one unlocalized list.
- A product request with no `sort` gets the category's configured default sort, applied by the
  API (`ProductDefaultSortingOptionProvider`). The SDK sends no `sort` when `sortField` is empty.
  `response.getSortField()` / `getSortDirection()` report what was actually applied.

## Behaviour (testable)

- [x] Both listings build their sort select from `productSortingOptions`, labels in the
      catalog's language (French labels on a `*_fr` catalog where the back-office has them).
- [x] A shop does not list another demo shop's fields: no `tbx_*` or `fio_*` option on the paper
      shop, no `llv_*` on the toolbox.
- [ ] Options of type `location` are not shown: distance sort needs a reference point the app
      does not have.
- [x] The default sort is not listed twice: there is no "Default" entry. On a category page the
      request sends no sort, and the select preselects the field and direction the API reports
      it applied. It keeps that default after the visitor picks another sort. Until the first
      result is in, a disabled "Default" placeholder is shown.
- [ ] Changing a category's default sort in the back-office changes the category page's first
      load, with no app change.
- [x] Search page: "Relevance" (`_score` desc, as before) is preselected. `category__position`
      is not offered on this page.
- [x] Relevance, Position, Price and Availability are in the catalog's language (storefront
      translations, see above); every other label is the API's.
- [x] Picking a field sets its natural direction: `_score` descending, everything else ascending.
- [x] A direction button beside the select switches ascending / descending. It shows an
      `arrow-up` (ascending) or `arrow-down` (descending) icon only; its `aria-label` and `title`
      name the direction ("Sort direction: Ascending"). It shows the shown sort's direction,
      including the default's. It is hidden for `_score` and `category__position`, which only
      make sense one way.
- [ ] If the options request fails, the select shows its placeholder and the page works.

## SDK contract used

- `getSearchManager().getProductSortingOptions(localizedCatalog.code)` - cached per catalog in the
  SDK, so both views and every remount share one request per catalog.
- `search({ sortField, sortDirection })` unchanged. An empty `sortField` on the category page
  still means "no sort sent".

## Tracking (required)

- None added or removed. Search and page view tracking is untouched.

## UI constraints

- One shared `SortSelect` component, used by both views. The direction button reuses the
  `.products-sort select` pill look, with `Icon` (`arrow-up` / `arrow-down`, added to
  `Icon.tsx`); no new token.
- New strings live in `common.json` under `sort`, in all three locales. The per-option keys that
  only the hardcoded lists used are removed from `category.json` and `search.json`.

## MUST NOT change

- `isServerFetchedView` in both views: page 1, no sort chosen, no filter. Showing the default
  as a preselected option must keep `sortField` empty until the visitor picks, so the
  server-rendered first page is still reused.
- `SHOP_FIELD_PREFIXES` only hides fields of _another_ demo shop. Unprefixed fields are shared
  and must stay listed in every shop.
- The label override in `useSortOptions` stays limited to the four codes the API hardcodes.
  Every other label belongs to the merchant and is already localized by the API.
- `fetchSearchProducts` in `src/sdk/server.ts` sends `_score` / `desc`, and the search page's
  first render must send exactly that, or the seeded page is refetched behind a skeleton.
- `fetchCategoryProducts` sends no sort, so the category's configured default applies on the
  server-rendered page as well.
